# Write 工具续轮修复报告

日期：2026-10-13（Asia/Shanghai）\
修复前基线：`f528e06`\
范围：仅 Write 调用识别、纠错及相关测试；报告中不包含凭据或用户文件正文。

## 结论

新附件出现的是普通文本 `Write {...} Bash {...}`。现有解析器只支持带工具标识的
`[tool_use:Write] id=... input=...` 和
`Previous assistant tool request/run: name=Write id=... input_json=...`，所以裸 Write
没有进入工具解析或纠错流程。这种响应会以 `end_turn`
结束，客户端无法执行文件写入，用户只能再次要求“请继续”。

本次增加裸 Write 的识别和一次原生结构化纠错，并收紧纠错结果的验收。成功结果必须为单个新的 Write
调用，失败结果明确报错，不能以“已完成”的普通文本静默结束。

## 本次识别并修复的问题

1. **裸 Write 被漏识别。** 识别独占一行、行内、多行 JSON 等裸 Write
   格式，仅将它作为纠错信号，不直接从无 id 的文本创建可执行调用。
2. **纠错缺少失败响应上下文。**
   重试携带被拒绝的响应，并明确说明客户端没有执行工具，帮助上游继续修正原调用。
3. **重试仍可返回普通文本。** 新增原生结构化验收；“已完成”自述和文本转录均不能被当作写入成功。
4. **重试可能返回其他工具、多个 Write、历史 id 或违反客户端 schema 的输入。** 纠错轮只提供声明的
   Write，且校验工具名称、数量、非空新 id、完整字符串参数、客户端 schema 和结束原因。
5. **重放上游可能重复服务端执行。** 首次响应包含服务端工具调用或结果时，阻止 Write
   自动纠错重试，返回原错误。

代码示例、行内代码、引用字符串、JSON 字符串、Write
正文、服务端工具结果中的同名文本，以及已经存在的结构化 Write，不触发裸 Write
纠错。`tool_choice: none`、未声明 Write、强制选择其他工具时也不启动该纠错入口。

正常工具、路由策略、模型映射、超时、心跳、统计、Bash/Read 的执行逻辑均未修改。上一版 SVG
引号兼容和坏 Write 阻断测试继续保留。

## 修复后的行为

```text
上游普通文本 Write 或无效 Write
  → 阻止下发
  → 检查请求是否允许 Write，以及是否已有服务端执行记录
  → 最多一次纠错，仅提供 Write，携带失败响应
  → 单个新的原生 Write 且参数符合 schema
  → 输出完整 tool_use，stop_reason=tool_use
```

纠错失败时返回明确的 502 后端错误；Deno 已开始的合成 SSE 返回流内 `error`，Bun
缓冲响应在下发流之前返回 HTTP 502。保留两种运行时现有的错误传输方式。

新增诊断事件 `unstructured_write_tool_input`；保留 `invalid_write_tool_input_retry` 和
`invalid_write_tool_input_retry_failed`。事件关联 requestId，不输出失败响应的完整正文。
