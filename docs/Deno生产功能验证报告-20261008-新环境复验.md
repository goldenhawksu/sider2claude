## 发现的问题

### P1：不同 `cid` 的相同请求体发生跨会话缓存污染

三次有界复测结果：

| 次数 | 首轮新会话 | 续轮 HTTP | 召回当前标记 | 返回会话 ID 匹配 |
|---|---|---:|---|---|
| 1 | A | 200 | 是 | 是 |
| 2 | B | 200 | 否，返回 A 的标记 | 否，返回 A 的 ID |
| 3 | C | 200 | 否，返回 A 的标记 | 否，返回 A 的 ID |

复现条件是同一 `AUTH_TOKEN` 下建立多个会话，并让不同会话发送完全相同的续轮请求体。首个续轮结果进入缓存后，后续会话会直接取回该结果。

根因可由源码直接解释：`deno/src/utils/sider-controller.ts:262-266` 的 `replayKey` 只包含调用者 `owner` 和去掉 `stream` 的请求体，没有包含传入的 `session/cid`，并在解析当前任务前直接返回缓存。由于所有客户端通常共享同一个服务 `AUTH_TOKEN`，影响范围可能覆盖同一服务凭证下的不同用户或任务。

影响：错误回答、返回错误会话 ID、跨任务内容泄露、后续请求继续串到错误上下文。该问题应作为生产阻断项处理。

建议修复与验收标准：

- 将规范化后的 `session` 纳入响应重放键；无会话和有会话必须明确区分。
- 保持“同一会话、同一请求”的幂等重放，同时隔离不同会话和不同认证主体。
- 增加回归用例：A/B 两会话使用相同续轮正文，各自返回自己的标记和会话 ID；同时覆盖 query `cid`、`X-Conversation-ID`、JSON/SSE 重放和不同 token。
- 修复后清理或自然淘汰旧格式缓存键，避免部署后 24 小时内继续命中旧值。

### P1：生产策略写入口无鉴权，遥测公开

- 无认证向 `/stats/strategy` 提交无效策略可到达业务校验并返回 400，证明路由未受认证保护。
- 源码 `deno/main.ts:108` 对合法 `conservative/pro/max` 会直接调用策略切换；本次为避免改变生产状态，没有发送合法值。
- `/stats/telemetry.json` 无认证返回 200 和原始遥测记录。

这属于生产安全和运维控制风险，而不是本轮核心协议失败。建议至少给策略写入口加 `requireAuth`，遥测端点限制为管理凭证或关闭公网访问，并记录策略变更审计。

### P2：浏览器 `x-api-key` 客户端的 CORS 预检不完整

带 `Access-Control-Request-Headers: content-type,x-api-key,anthropic-version` 的预检返回 204，但响应仅允许 `Content-Type,Authorization`。`deno/main.ts:47` 的全局 CORS 配置遗漏了 `x-api-key` 和 `anthropic-version`，浏览器会在真正请求前拦截。

建议补充这两个请求头；如浏览器需要读取会话和诊断信息，还应按需暴露 `X-Conversation-ID`、`X-Request-ID`、`X-Backend-Used` 等响应头，并把 CI 预检用例改为携带真实请求头断言。

### P2：畸形 JSON 被归类为 HTTP 500

`POST /v1/messages` 的畸形 JSON 返回 `500 api_error`。有效但缺字段的请求已经正确返回 400，因此解析错误也应归类为 `400 invalid_request_error`，避免 SDK 将客户端错误当作服务故障重试。

根因位置为 `deno/src/routes/messages-hybrid.ts:107` 的 JSON 解析异常落入 `:370-380` 的通用 500 分支。

### P3：冷启动与响应头

- 连续 5 次健康检查中，首个请求 9.50 秒，后续 4 次为 265-268 毫秒。样本很小，不能当作 SLA，但应关注冷启动对探活超时和首次请求体验的影响。
- 实测响应没有 HSTS、`X-Content-Type-Options`、`X-Frame-Options` 和显式缓存控制头。Deno 平台可能承担部分 HTTPS 策略，但从客户端响应看这些头不存在；建议按实际威胁模型补齐。
