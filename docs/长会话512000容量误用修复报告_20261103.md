# 长会话 512000 字符容量误用修复报告

日期：2026-11-03（北京时间）。基线：`6c62a43`。

## 问题与根因

附件记录了 SVG Write 之后的错误：

> API Error: 400 待登记内容超过可信内容库单项512000字符容量，请压缩会话历史或缩短正文

随后两次 `/compact` 也返回同一错误。附件没有完整 HTTP 请求、生产地址和模型名，因此本轮使用合成 SVG 历史复现相同错误，没有把本地结果当作生产复验。

两套运行时的 `upload(context)` 调用通用 `saveControllerText`。该函数同时保存会话历史、文件正文和回复缓存，统一拒绝超过 512000 字符的文本。会话历史超过此值时，在首次上游调用之前就返回 400；压缩形态请求仍需登记历史，因此同样失败。该限制与 HTTP 请求体默认 32MiB 上限不同，也不是附件中单个 SVG 的大小。

## 修复

- `saveControllerText` 保留默认 512000 字符限制，增加内部调用可指定的字符上限。
- 仅上下文上传不套用单份文件正文的限制，由既有 HTTP 请求体上限控制输入体积。
- 保持 8000 字符存储分块、SHA-256 校验、保留期限和上传检查点结构；已有任务无需迁移。
- StoreContent、Read 正文引用和回复缓存继续使用原有容量限制。
- 容量错误只建议缩短正文，避免再次建议会被相同错误阻塞的会话压缩。
- 更新集成套件 16，将原来断言超长会话返回 400 的用例改为验证摘要保留尾部事实。

没有增加环境变量、替换模型、截断历史或改变路由。

## 复现与验证

修复前，Deno 与 Bun 各执行 5 项容量测试，均为 **1 通过、4 失败**：普通续轮与压缩形态请求在 JSON、SSE 下全部得到预期之外的 400；文件正文容量边界测试通过。

修复后，上述 8 项失败用例全部通过，断言每次上游载荷长度、分片顺序、父消息连续性、拼接后的完整历史，以及最终响应的尾部标记。

补充覆盖超过 512000 字符的中断后追加继续、KV 中中文及 emoji 原文的完整回读与哈希校验，以及重建控制器和存储适配器后续传。已确认分片不重复发送，未确认分片从正确父节点重试。Bun 的压缩形态用例使用 SQLite 保存上下文。

## 交付边界

本报告记录发布前的本地修复与确定性验证；真实集成套件 16 仅完成类型检查。用户在获知本地验证结果及尚未上线的状态后，明确要求提交 main 并推送远程。本次按该授权发布，不把确定性测试表述为真实上游集成门禁或生产复验通过。生产目标可从未跟踪的历史发布配置读取，地址和凭据不进入版本控制。

解除本地存储容量误用不代表上游支持无限上下文。长历史仍需要多次登记；真实上游额度、ACK 行为及总期限继续生效。新版本上线后，应先核对部署标识，再验证健康、模型、鉴权、CORS，以及长历史续轮和压缩形态请求。
