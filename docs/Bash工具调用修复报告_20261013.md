# Bash 工具调用修复报告

日期：2026-10-13（Asia/Shanghai）\
修复前基线：`07c2638`\
范围：Anthropic 兼容后端的裸 Bash 文本调用识别与协议纠错，Bun/Deno 同步。

## 原因与证据

请求 `req_mv5zubq5_318e8f7f` 携带 121 条消息、17 个工具。上游为 `glm-5.3-flash`，耗时 11677
ms，最终返回 `end_turn`、1 个内容块。

附件中的两次停顿均出现以下格式：

```text
Bash
{"command":"python ...","description":"..."}
```

它是普通文本，没有原生 `tool_use` 块，也没有已有文本兼容协议要求的工具 id 和 input
前缀。原解析器不识别这种形式，响应以 `end_turn` 正常结束，客户端因此没有执行命令。此前 Write
的专属修复没有包含 Bash。

附件随后出现的 Bash `IN/OUT` 表明该次结构化调用已经执行，质量检查器返回 0
错误及警告；这些警告不是本次代理故障的原因。

`upstream_slow_response` 表示超过 10 秒的告警阈值，不代表超时。POST 200
及流起始时间也不能作为命令已经执行的证据。日志未提供完整原始上游响应，本地以附件同形文本重现了该问题。

## 实现

1. 识别裸 Bash 的独占一行、行内、多行 JSON 形式；跳过代码围栏、行内代码和引用字符串。
2. 只提取单个完整、严格 JSON 的 Bash 参数，不修补或猜测命令。参数先通过客户端声明的 schema 验证。
3. 最多一次协议纠错：携带失败文本，仅提供声明的 Bash，要求返回单个新 id 的原生结构化调用。
4. 纠错后的所有参数必须与原输入一致，包括命令、说明、引号、反斜杠、管道、重定向、换行、超时及后台执行选项。字段顺序可以不同，值和字段集合不能变化。
5. 成功时下发完整 `tool_use`，并将结束原因归一化为
   `tool_use`；失败返回明确错误，不能接受“执行完成”的普通文本。

截断 JSON、空命令、多个裸 Bash、schema 无效输入不进入自动纠错。未声明
Bash、`tool_choice: none`、强制其他工具、已经存在原生客户端调用时不启动裸 Bash
纠错。出现服务端执行记录时不重放上游请求。

代理负责装配调用，命令继续由实际客户端执行。修复不会在代理服务端执行附件中的 Python 脚本。

GLM，未运行附件中的实际项目脚本，也未部署远程服务。本地验证证明代理能够识别、纠错和正确下发调用；实际执行成功仍需要客户端成功的
`tool_result`。

新增事件为
`unstructured_bash_tool_input`、`invalid_bash_tool_input_retry`、`invalid_bash_tool_input_retry_failed`，通过
requestId 关联，不把完整命令写入诊断日志。

对同一请求，成功链路应为：识别裸 Bash → 一次协议纠错 → 下发 Bash `tool_use` → 客户端执行 → 返回
`tool_result` → 正常续轮。单次纠错会增加一次上游往返，没有降低模型生成耗时的保证。
