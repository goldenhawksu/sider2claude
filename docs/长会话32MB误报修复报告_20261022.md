# 长会话“max 32MB”误报修复

## 现象与复现

制作 PPT 到 P07 后，Read `spec_lock.md` 反复显示：

```text
Request too large (max 32MB). Try with a smaller file.
```

生产旧版本使用合成请求实测：请求仅 **406,393 字节**，返回 HTTP 413，
`X-Sider-Controller: true`，原始错误为：

```text
上下文超过单次可登记的16个分段，检查点保留
```

因此已确认代理存在远小于 32MB 即返回 413 的路径。未取得用户原始 HTTP 请求体，
不能据粘贴日志确定其精确字节数；本次复现与连续 SVG 历史增长后的失败过程一致。
预览服务两小时空闲退出、P03 的 XML 引号问题是附件中的其他事件，不是该容量判断的触发条件。

## 根因

主控将长上下文切成小片发送给 Sider，但最多只允许 16 片。Deno 默认每片正文
5488 字符，完整历史超过约 87808 字符就会被拒绝。这个内部容量错误使用 HTTP 413，
客户端会展示通用的 32MB 请求过大提示，使用户误以为刚读取的文件太大。

另一个续传缺口是：首片成功就会保存 Sider 会话 ID，失败后的重试据此只发送当前增量，
未发送的历史尾部可能被跳过。已有分片进度本身不足以恢复，必须同时保存待上传的原文。

## 实现

- 移除 16 片限制；单次发往 Sider 的小片大小保持原有配置。
- 待上传原文复用既有分块存储和 SHA-256 校验，任务仅增加可选的待上传哈希。
- 首片发送前等待原文落库，只有模型明确确认接收才推进分片序号。
- 重试先续传原始内容的剩余部分，完成后才构造和发送当前增量，保留新增的“请继续”指令。
- 已确认分片不重发；原文缺失或哈希不一致时明确失败，禁止猜测、截断或跳过尾部。
- 内部内容库及单次输入配置错误返回明确的 400，显示实际容量；真正上游 603 对应的 413 语义保持。
- 两套运行时同步修改，不需要数据迁移，旧任务没有新增字段时沿用正常路径。

容量边界保持明确：单份待登记内容使用既有内容库 **512000 字符**上限，超过后提示压缩
会话历史或缩短正文。此限制是应用内容库边界，与 HTTP 32MB 或某个 Read 文件的大小不同。
本次没有扩大 HTTP 请求体上限，也没有丢弃历史来绕过容量检查。

## 验证

修复前新增的三项 Deno 回归全部失败：超过 16 片返回 413，追加继续后漏掉尾部，
内容库容量错误被伪装成 413；修复后全部通过。

```text
npm run test:regression

  Bun：120 pass，0 fail

deno check deno/test/integration/run.ts
npm run build
git diff --check
```

新增集成套件 16 覆盖：超过两套运行时 6000 字符配置下的 16 片阈值、历史尾部唯一规范路径、
工具请求重放、追加继续后的同任务续轮，以及 512000 字符容量错误。工具反馈使用合成数据，
不操作真实 PPT 文件；模型与 API 集成调用使用真实服务。

Deno 真实严格门禁：套件14全部13项、套件15的窗口工具续轮1项、新套件16的2项，共16/16通过，零失败、零上游受限（1167.4秒）。其中P08请求99419字节，完整尾部路径、Read重放和追加继续全部通过。

Bun真实HTTP及SQLite验证：新套件16的2项一次通过，零失败、零受限（323.6秒）。同样保留历史尾部路径、重放响应和追加继续指令。
