# Bash 生产纠错失败修复报告

日期：2026-10-13（Asia/Shanghai）\
问题版本：`v1.0.0`／`c12274f`\
范围：Bash 裸文本参数恢复与续轮；Bun/Deno 同步。

## 日志定位与证据边界

用户日志中 Step 7.1 拆分备注返回 15/15 成功，Step 7.2 后处理也返回 Done。这两条命令已有客户端
`IN/OUT`，失败发生在后续请求的代理 Bash 纠错验收。

错误文本唯一定位到 `validateBashRetryResponse()`。旧实现将一个已经完整解析且符合客户端 schema 的
Bash
调用重新发送给模型，要求返回原生结构化调用，再对工具数量、id、字段集合及所有字段值逐项比较。模型省略说明字段、增加默认
timeout、自述完成、返回文本转录或再次选用其他工具，都可能触发同一条泛化错误。

该日志没有 requestId 或被拒绝的上游重试
input，不能断言本次旧失败具体命中了哪个条件。已确认的是：不必要的第二次生成和全字段比较使完整合法的原调用受到模型再次输出的影响。确定性测试复现了说明省略及默认字段添加导致的旧版拒绝，以及“Step
7.1／7.2 成功后继续导出”的续轮场景。

部署前生产 `/health` 返回 200，版本为 `1.0.0+fceb5d1f`。一次无文件访问的真实 GLM
基础纠错探针通过，说明该问题并非每次请求都发生；不能把这次简单探针当作原故障已复现。

## 修复

完整、唯一、严格 JSON 且通过客户端 schema 的裸 Bash 参数由代理直接装配为客户端
`tool_use`，所有原字段和值保持不变，不再请求模型二次生成。这与已有文本工具转录的协议还原职责一致；命令仍由客户端执行。

保留并补充以下边界：

- 截断、空命令、多个裸 Bash、重复字段（包括转义后同名字段）、schema 无效输入仍阻断，绝不猜测命令。
- 代码示例、引用字符串、历史回顾及否定执行指令保持普通文本。
- 已有原生工具调用时保留原调用；未声明 Bash、禁止工具或强制其他工具时不恢复裸 Bash。
- 检测到服务端执行记录时不恢复该裸调用，避免误判执行状态。
- 仅返回成功 `tool_result`
  的自动续轮中，重复相同已执行命令会被阻断；失败结果后的重试及用户明确重新执行仍可继续。
- 标识由请求上下文与参数生成，同一请求重试保持相同 id，新的明确执行请求获得新 id。

Write 纠错与验收、路由、配置、超时及其他工具解析规则没有修改。删除旧 Bash
专属二次生成与比较方法，简化该路径。

## 诊断

成功事件为 `bash_tool_input_normalized`，记录 requestId、来源
`strict_json`、命令字符数和参数保真标记，不记录完整命令。

拒绝事件为 `invalid_bash_tool_input`，附明确原因：

| 原因                            | 含义                                |
| ------------------------------- | ----------------------------------- |
| `incomplete_or_ambiguous_input` | 不完整、重复字段或无法确定唯一调用  |
| `schema_invalid`                | 原参数不符合客户端 schema           |
| `upstream_incomplete`           | 上游未正常完整结束，例如 max_tokens |
| `server_execution_present`      | 本轮已有服务端执行记录              |
| `successful_call_replayed`      | 自动续轮重复上一条成功命令          |
