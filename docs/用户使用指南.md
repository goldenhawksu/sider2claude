# Sider2Claude 用户使用指南

适用基线：2026-10-12，代码提交 `451a4f2`。本指南帮助你将 Sider2Claude 接入 Claude Code、cc-switch 和 VS Code 插件。

## 1. 准备服务和凭据

本地服务器选择 Bun 或 Deno；npm／TypeScript 构建使用 Node.js。项目的 CI 当前使用 Bun 1.3.x、Deno 2.9.x，其他版本需验证。

在仓库根目录运行：

```bash
npm ci
```

准备三类独立凭据：

| 凭据 | 放置位置 | 用途 |
| --- | --- | --- |
| 自己设定的客户端 token | 服务端 `AUTH_TOKEN`；客户端 API key／`ANTHROPIC_AUTH_TOKEN` | 客户端访问本代理 |
| Sider token | 服务端 `SIDER_AUTH_TOKEN` | 代理调用 Sider |
| Anthropic 兼容后端 key | 服务端 `DEEPSEEK_API_KEY` | 工具、视觉和 XML 分类能力 |

将服务端配置写入未跟踪的 `deno/.env`。两个运行时都优先读取它；该文件不存在时才读取根 `.env`，运行时环境变量优先于文件。

```env
PORT=4141
AUTH_TOKEN=your-client-token
SIDER_AUTH_TOKEN=your-sider-jwt
DEEPSEEK_BASE_URL=https://api.deepseek.com/anthropic
DEEPSEEK_API_KEY=your-compatible-api-key
DEEPSEEK_MODEL=deepseek-v4-flash
SIDER_CONTROLLER=false
SIDER_STRATEGY=conservative
DEFAULT_BACKEND=sider
AUTO_FALLBACK=true
PREFER_SIDER_FOR_CHAT=true
```

如使用 Z.ai，改为 `DEEPSEEK_BASE_URL=https://api.z.ai/api/anthropic`、`DEEPSEEK_MODEL=glm-5.3-flash`，并填写该入口对应的 key。模型名和 key 必须与实际 provider 匹配。

## 2. 启动并检查

任选一种启动方式；上述配置统一使用 4141 端口：

```bash
bun run dev
# 或
deno task start
```

PowerShell 检查：

```powershell
Invoke-RestMethod http://localhost:4141/health
Invoke-RestMethod http://localhost:4141/v1/models
```

确认健康状态为 `ok`，且目录包含所选模型。修改环境配置后重启服务；若端口被占用，先查明进程归属再处理。

未配置 `PORT` 时，Bun 默认 4141，Deno 默认 8000。远端用户使用部署方提供的私有地址，无需启动本地服务器。

## 3. 连接 Claude Code 与 VS Code

直接连接时可配置客户端环境：

```powershell
$env:ANTHROPIC_BASE_URL='http://localhost:4141'
$env:ANTHROPIC_AUTH_TOKEN='your-client-token'
$env:ANTHROPIC_MODEL='claude-sonnet-5.5'
$env:ANTHROPIC_DEFAULT_SONNET_MODEL='claude-sonnet-5.5'
$env:ANTHROPIC_DEFAULT_OPUS_MODEL='claude-opus-5.5'
$env:ANTHROPIC_DEFAULT_HAIKU_MODEL='claude-haiku-5.5'
```

也可参考[客户端 JSON 模板](../config/claude-code.sider-controller.json.example)。按客户端支持的设置方式载入配置后，重新启动 Claude Code 会话或 VS Code 插件，使新 provider 生效。

这些客户端变量不会配置服务端的 Sider 或兼容上游。客户端 token 填 `AUTH_TOKEN`，不要填 Sider token 或上游 key。

## 4. 通过 cc-switch 接入

在 cc-switch 中为 Claude 添加 Anthropic 兼容 provider：

1. Base URL 填 Sider2Claude 服务地址，不附加 `/v1/messages`。
2. API key 填该服务的 `AUTH_TOKEN`。
3. Sonnet、Opus、Haiku 选择目录中的模型原名，例如 5.5 系列。
4. 启用该 provider；若使用 cc-switch 本地代理，让插件连接其代理地址。
5. 重新启动插件会话，先测试普通对话，再读取一个已知文件确认工具循环。

cc-switch 不同版本的配置字段可能不同，以该版本的 provider 表单为准；服务接收标准 Anthropic `model` 字段。

可以保留 cc-switch 的 1M 声明。模型名 `claude-sonnet-5.5[1M]` 发给 Sider 时会规范化为 `claude-sonnet-5.5`；响应仍保留请求名。原名与窗口标签共享新版本主控状态、重放和限流，但声明 1M 不表示 Sider 实际有 1M 输入容量。

## 5. 选择主控模式

混合路由适用于由兼容后端补齐客户端工具能力。若希望 Sider 负责规划、创作和工具选型，开启主控并选择本运行时的配置：

| 运行时 | 主控配置 |
| --- | --- |
| Deno | `SIDER_CONTROLLER=true`；如要接管插件的流式请求，再设 `SIDER_CONTROLLER_STREAMING=true` |
| Bun | `SIDER_CONTROLLER=true` 后接管非流式与流式；没有单独的流式开关 |

模板见 [Deno](../config/sider-controller.deno.env.example) 和 [Bun](../config/sider-controller.bun.env.example)。主控模式需要可用的持久化存储，Deno Deploy 需关联 Deno KV，Bun 运行目录需可写。

Deno 默认单次新增输入上限 6,000 字符，Bun 为 14,000；更长内容完整分段，单次最多 16 段。输入、工具定义、正文引用与配额均有边界，详见[主控说明](Sider主控模式.md)。

无工具 XML 安全分类使用已配置的原生兼容后端，包括开启主控时。代理保留真实分类判定和错误；分类成功并不等于待评估命令已执行。

## 6. 使用 ppt-master 生成 PPT

先确认客户端能读取技能文件、模板与素材，再发起 PPT 制作任务。工具调用的实际执行由 Claude Code／MCP 完成：

1. 读取 ppt-master 技能与模板说明。
2. 抓取资料；来源失败后根据工具结果选择其他来源。
3. 生成页面与清单，并通过 Write 保存。
4. 执行客户端质量检查、背景图处理和导出管线。
5. 检查导出文件、页面数量与质量报告。

Sider2Claude 提供 API 与工具协议转换。PPT 完成的证据是实际产物和客户端检查结果，不能仅凭助手说“已完成”。

对于明确给定的原文，可以使用以下边界：

```text
请使用 Write 原样保存正文。
目标路径：C:/project/facts.txt
正文开始
需要完整保留的正文
正文结束
```

只有客户端声明 Write、模型选择可解析的单个 Write 且参数通过校验时，兼容适配器才会用用户原文恢复路径与正文。无效 JSON 仍会被阻止；正文业务格式另由客户端校验。

主控的 `StoreContent → WriteFromRef` 会最终变成客户端 Write。写入成功且满足 Read 回读条件时，代理继续验证字符数和 SHA-256；回读失败会要求使用原引用重写。

## 7. 排查常见问题

| 现象 | 检查与处理 |
| --- | --- |
| `ECONNREFUSED` | 核对服务是否启动、端口、代理地址与网络；用 `/health` 探活 |
| 401 | 核对客户端 key 与服务端 `AUTH_TOKEN`、cc-switch 实际选中的 provider，以及 `deno/.env` 优先级 |
| `[1m]` 模型不可用 | 确认部署包含窗口修复；主控要使用目录中的基础模型。仅客户端错误文字不足以判断上游原因 |
| Bash auto 模式暂不可用 | 查找对应分类请求及 `rule_0_safety_classifier`；核对 `DEEPSEEK_*` 配置，检查最终 HTTP／流内错误 |
| HTTP 413 或 Sider 603 | 输入或分段超限；检查实际历史、system 和工具定义，按客户端工作流压缩历史或拆分任务 |
| HTTP 429 或 Sider 1135 | 按非流式 `Retry-After` 和上游建议等待；主控检查点保留，不通过改标签绕过冷却 |
| `invalid_write_tool_input` | 上游 Write JSON、路径或正文无效；保留 requestId，要求重新生成结构化调用，检查实际文件格式 |
| 上下文分片未确认／协议拒绝 | 查看 `context_unconfirmed`／`tool_protocol_refused`；不要把拒答当成登记成功，检查载荷是否已乱码 |
| 网页工具 MCP -400 | 检查工具自己的 URL 规则和来源；已有客户端网页工具时代理会提示优先客户端执行 |
| 已收到流开始却一直无正文 | `message_start`／ping 仅表示连接存活；继续检查 `stream_failed`、`upstream_timeout` 与流内 error |

反馈问题时提供 requestId、时间、请求模型、HTTP 状态和最终错误；不要公开 token、私有部署地址或完整敏感正文。

## 8. 验证更新是否生效

Deno 生产 `/health` 的 `version` 包含部署标识，例如 `1.0.0+<部署片段>`；它不是 Git 提交哈希。配合部署平台的提交记录确认版本，再验证窗口模型与分类路径。

代码基线的测试范围见[窗口修复报告](cc-switch上下文窗口兼容修复_20261012.md)。本地真实上游验证、真实客户端验证与生产验证分别记录，不能互相替代。
